# Sprint 3 — unified search

See [ADR-0019](../adr/0019-derived-unified-search.md), [implementation plan](../02-architecture/sprint-3-plan.md), [knowledge graph](../03-data/knowledge-graph.md) and [local setup](local-development.md). PostgreSQL is authoritative; OpenSearch contains disposable public projections only.

## Local operation

Reuse the existing PostgreSQL/PostGIS and OpenSearch containers. Run `pnpm install --frozen-lockfile`, `pnpm db:migrate`, `pnpm db:migrate:test`, then `pnpm search:reindex`. Start `pnpm search:worker` alongside `pnpm dev:api` and `pnpm dev:web`. Do not publish fixture-backed drafts merely to populate search. With no approved canonical entities, public search correctly returns empty results.

Commands:

- `pnpm search:reindex`: build fresh physical indexes and atomically swap all three aliases after successful bulk delivery. Previous generations are retained.
- `pnpm search:sync`: consume a pending canonical generation and send only hash-changed documents/deletions. First run or missing index family rebuilds automatically.
- `pnpm search:reconcile`: force a public snapshot/hash comparison even if no changes are pending.
- `pnpm search:worker`: poll every two seconds, reconcile each minute, retry failures with bounded exponential delay up to 30 seconds. Normal signals stop waiting promptly. Only completed jobs advance the checkpoint.
- `pnpm search:status`: report current/processed generation, last indexing time and whether canonical changes are pending. Generation difference is a change marker, not an entity count.

`SEARCH_INDEX_PREFIX` is empty by default, giving aliases `destinations_v1`, `places_v1`, `experiences_v1`. A stable prefix isolates deployments and test indexes; PostgreSQL manifests/checkpoints are namespaced too. Future `content_v1`, `partners_v1`, `products_v1`, `events_v1` are descriptors only and are never created by the worker. A full index version change requires changing the descriptor/mapping and rebuilding.

`OPENSEARCH_URL` is the API read endpoint. `OPENSEARCH_INDEX_URL` optionally supplies the worker writer endpoint; URL credentials are redacted from errors. Use TLS and separate read-only/indexing service roles in production. Security-disabled, loopback-bound single-node development Compose is not a production security policy. The Compose `search-worker` app profile uses the API image with a separate bundled job command, restart policy and no exposed port. Apply migrations before starting it; no migrations are run silently by workers. Bundle is `dist/tools/search-index.cjs`; run it with `sync`, `worker`, `rebuild`, `reconcile` or `status`. Docker image builds/deployment require separate operational validation.

For a populated local UI preview, stop the ordinary API and run `pnpm search:preview` with `pnpm dev:web`. The preview requires an isolated `_test` database, creates synthetic canonical data and its own index namespace, and prints example URLs. Normal shutdown withdraws only its fixtures and removes its indexes, checkpoint and temporary media. Abrupt termination can bypass cleanup. Never run preview alongside integration tests or use its facts as production content.

## Delivery and canonical authority

Search owns `search_state` and `search_manifest`. Statement triggers mark public projection dependencies dirty in the same PostgreSQL transaction, including registry/Geo/Place/Experience/DestinationProfile, graph edges, sources and editorial references. This catches direct SQL publication, source retirement and hierarchy edits. Search does not mark ContentOutbox delivered or own canonical writes.

A PostgreSQL session advisory lock serializes jobs; a competing job reports busy. No external call occurs inside a canonical write transaction. A worker reads an observed generation, obtains the shared public discovery projection, compares SHA-256 hashes with its manifest, bulk-writes bounded batches, checks per-item failures, then transactionally updates its manifest/checkpoint. Failed/crashed delivery is retried from current canonical data. A newer change committed during indexing remains dirty. Deletion, unpublish, geographic-owner withdrawal and source retirement remove documents on the next successful sync. There is no exactly-once claim.

Public search obtains current eligible canonical UUIDs and destination associations before querying OpenSearch. Eligibility matches Sprint 1–2 and independently gates identity/profile/owner/edge/source. Engine queries are constrained to that UUID set; returned cards use current PostgreSQL names/summary/verification/URLs rather than stored index text. Thus a withdrawn identity is hidden without waiting for index delivery. New published content becomes searchable after indexing; during lag, matching/ranking may reflect the previous projection. Canonical storage or search failures return 503; no synthetic fallback is served. An empty canonical dataset returns an empty result without requiring an initialized index.

MVP bounds: a 20000-entity projection/eligibility cap, snapshot reads with hash-diffed incremental writes, one shard per index and zero replicas for local single-node operation. Before larger scale, measure lag/query time and introduce per-owner changes/fanout, keyset/bulk projections and batched per-hit eligibility. Global generation invalidation is intentionally coalesced and may serialize brief dependency writes; it is not per-row streaming. A reconciliation compares canonical hashes to the durable manifest; out-of-band edits to OpenSearch document contents require a rebuild, not just hash reconciliation. Only the worker may write indexes.

Rebuild failures leave current aliases untouched. An alias-switch/manifest crash is recoverable by current-data retry. Missing family indexes force rebuilding all three. To roll back mappings, atomically point the three aliases at an inspected prior generation, then force a rebuild/sync appropriate to current canonical data. Do not blindly roll back canonical content with aliases. Retained generations/orphaned failed rebuilds need operator inspection and eventual deletion; commands never delete unrelated indexes. Monitor pending generations, indexed time, worker failures, shard/disk pressure and retained-generation count. Alert on lag over 60 seconds; this is a target, not a measured production SLA.

## API and UI

`GET /api/v1/search` accepts `q` (trimmed 1–120 characters), `type` (DESTINATION/PLACE/EXPERIENCE), `destination` (approved canonical slug), `page` (1–100), optional `locale` (default en), `autocomplete` (true/false) and an optional paired `lat`/`lon`. Unknown keys/types, malformed slugs and incomplete coordinates return 422. Query text is passed into safe match clauses, never raw query-string DSL or arbitrary index names. Swagger documents these parameters.

Response contains query/page/pageSize, combined total, maximum group page count, groups with type/total/current canonical results and eligible suggestion links. Normal pages contain up to 12 results **per group**; the same page number applies to each group. Autocomplete returns up to five per group, with bounded UI suggestions. Global ordering across different index scores is not asserted. `destination` is a hard current graph filter; destination context without the filter can help discover connected attractions/concepts. Optional coordinates add a small proximity signal only for actual canonical points; they never invent route access or travel times.

`/search/` renders grouped meaningful HTML on the server, query/type/destination controls, source-freshness dates, internal detail links, pagination, suggestions and empty/unavailable states. Every search variant is noindex/follow, canonicalized to `/search/`, and excluded from the sitemap. Homepage, discovery pages and editorial detail offer a global search field. Autocomplete is same-origin through `/api/search/`, debounced and abortable; keyboard arrows/Enter/Escape, combobox semantics, announcements and error states are supported. Entity details retain their existing canonical SEO pages.

## Ranking and relevance

Name exact boost 25; phrase matching boosts name/alternative-name phrases; full-text weights name 8, alternative names 6, category/tags 3, approved destination/ancestor context 2, summary 1. A lower-weight combined public text field allows mixed destination/activity queries to satisfy AND across fields. Prefix matches use search-as-you-type name/alias fields. Fuzzy text uses AUTO edits with bounded 25 expansions. Stable UUID breaks score ties. Explicit geographic proximity contributes at most 0.2 score. No payments, subscriptions, partners, impressions, sponsorship or invented popularity signal is accepted.

Unicode standard tokenization, lowercase/asciifolding and Urdu character normalization preserve supplied canonical English, Urdu and romanized alternatives. No unsupported transliteration is automatically added. Curated query-time synonyms cover northern-area terminology, hiking/trekking, boat/boating, family activities/suitability, food/cuisine, heritage, photography and camping. The explicit “family activities”/“family suitable” intent requires a true canonical suitability value; unknown/false records are excluded. A synonym does not establish suitability. New aliases/Urdu spellings and category vocabulary need source/editorial governance.

[The 80-case dataset](../../tests/relevance/pakistan-search.json) covers destinations, eight attractions, concepts, supplied Urdu names, romanizations, common misspellings, synonyms, context and prefix queries. Each judged case must find its intended canonical UUID in the first three results in its entity group against real OpenSearch. Synthetic isolated fixtures prevent approving production facts. This is a regression benchmark, not a guarantee of real traveler satisfaction. Add approved multilingual queries and judged negative/ambiguous cases as content expands. Analyzer/synonym changes require rebuild and this suite before release.

OpenSearch design references: [multi-match](https://docs.opensearch.org/latest/query-dsl/full-text/multi-match/), [autocomplete](https://docs.opensearch.org/latest/search-plugins/searching-data/autocomplete/). The application separately tests bounded fuzzy matching and prefix matching because fuzzy edits do not apply to the final prefix token.

Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm build`, `pnpm format:check`. Integration tests require the existing live OpenSearch endpoint and isolated PostgreSQL `_test` database; unique test index prefixes are cleaned on normal completion. Do not run preview concurrently with integration tests because CMS fixture template assignments are shared within that isolated database.
